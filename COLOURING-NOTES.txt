Colouring station — v160.7
==========================

Scope
-----
Shared complete colour schemes are extracted from non-hidden, controllable unit
families (body, weapons and parts together), grouped by colour-table similarity,
then bounded by BOTH a hard maximum of 20 schemes and a 144 MiB bulk-RGBA budget.
No turret, missile/internal-unit, or per-component palettes are generated.
Each selected complete scheme is consistently applied to every target unit family.
The current repository produces 8 schemes / 472 hidden variants, not 94 / 5,546.
Schemes have separate armour and accent shade roles; neutral armour never indexes
into a mixed hue/brightness list. Alpha pixels and dimensions are preserved.
Cell/heat/glow/light masks are copied unchanged. Corrode and Dissociate share one
scheme because their source colours are identical; old cans alias to it.

Bulk sprite copies cover active unit bodies, weapons, legs, treads and parts.
Recoloured wrecks and full/UI icons are excluded from the bulk datapatch. Composite
full icons live in the server-only preview cache and are streamed on selection.
One client preview texture name is reused so browsing does not accumulate textures.
Unrelated terrain/building/UI/background textures are never multiplied by schemes.
Old generated directories are replaced on fingerprint changes (including v17 files).
Old per-unit paint cans are migrated to the shared scheme; retired saved variant
names resolve to their shared replacement or original base unit rather than dagger.
Old turret paint cans are retired but remain decraftable for their normal recipe
materials (subject to existing storage/overflow rules); they cannot be crafted anew.

Generated output (not embedded in coolplugin.jar):
  config/assets/sprites/colouring-generated/
  config/assets/content/units/colouring-generated/
  config/assets/content/blocks/colouring-generated/
  config/assets/patches/zzzz-colouring-upgrades.hjson
  config/colouring-cache/manifest.json
  config/colouring-cache/previews/ (server only, not a datapatch image folder)

On first start, the plugin fetches the official pinned v160.7 desktop JAR to read
vanilla sprites headlessly. To use a local source instead, launch Java with:
  -Dcoolplugin.colouring.vanillaJar=/absolute/path/Mindustry.jar
The source download and atlas extraction are cached under config/colouring-cache.
Changed image/palette inputs invalidate recoloured PNGs. Definitions are refreshed
on each start. New definitions/images are staged before publishing to assets.
Generated hidden variants do not feed back into palette discovery or unit fallbacks.

MEMORY MEASUREMENT
------------------
Current data: 485 active source regions x 8 shared schemes = 132.0 MiB raw RGBA.
The exact Arc PixmapPacker (4096px pages, 2px duplicate borders), including all
original patch sprites and generated station/can sprites, measured THREE pages:
192 MiB of atlas textures in five tested insertion orders. This is the patch atlas,
not total game/process memory. Temporary decoder/pixmap copies and the vanilla
atlas are additional. Conservative generation-time padding estimate: 250.9 MiB.
This replaces v17's roughly 3.6 GiB uncompressed bulk sprite set.
The 144 MiB generation budget lowers scheme count automatically for larger content
packs; it is not permission to expand to 20 schemes regardless of texture cost.
Full hidden-variant parsing and a full native OpenGL menu run were tested.

Gameplay
--------
Tier I: 3x3 PayloadConveyor, payload limit 3 tiles (unit hit size <=24 world units).
Tier II: 5x5 Reconstructor-style holder accepting larger unit payloads. Its self
upgrade entries are inert (effectively infinite construction time); recolouring
is controlled by the plugin, not a reconstruction recipe.
Both stations are added to the existing player's tech tree under payload-conveyor
(Tier II under Tier I), including migration of an existing saved tree.

Enter with the player-controlled unit using normal payload-entry controls.
The plugin opens a native MenuBuilder dialog and locks the holder. The current or
selected full unit preview stays on the left, including empty inventory and already
painted units. Owned paint icons occupy the right hexagonal panel; selection has an
accent glow. Owned T2 cans remain visible but disabled at T1 with the message
"Requires colouring station 2" below their button. Palette selection is free; Apply
consumes one can. Vanilla-derived shared schemes work at Tier I or II. Patch-derived shared schemes
require Tier II. Every can is an autogenerated Workbench placeholder recipe costing
50 copper + 25 lead, in the existing ten-slot inventory.
No cans: "You dont have any paint cans on you".
No custom Exit button: vanilla supplies the close control.

Closing the menu or /exit releases the payload and removes the menu lock. If nearby
terrain/units prevent dumping, the payload remains intact and the player is asked
to clear space and retry /exit; no payload is deleted or duplicated.
Unit identity, health/shield, inventory/cargo and weapon runtime state are retained.
The selected type is saved through existing faction unit persistence. Ordinary
reconstructors receive palette-preserving upgrade entries.

Validation
----------
Build:
  JAVA_HOME=/path/to/jdk17 bash gradlew jar -PserverJar=/path/server-release.jar

Full palette/unit parsing + station tests:
  JAVA_HOME=/path/to/jdk17 MINDUSTRY_JAR=/path/Mindustry.jar \
  SERVER_JAR=/path/server-release.jar bash tools/colouring-validation.sh

The test fixture is written to .cache/colouring-validation by default. Set
OUTPUT_DIR to change it; PALETTE_LIMIT can reduce the fixture for quick tests.
Do not set coolplugin.colouring.testPaletteLimit on a production server.

Measure with the real Arc atlas packer as well:
  MEASURE_ATLAS=1 JAVA_HOME=/path/to/jdk17 MINDUSTRY_JAR=/path/Mindustry.jar \
  SERVER_JAR=/path/server-release.jar bash tools/colouring-validation.sh
